# v0.8.0 — storage encoding for the bundled reference arrays

Ratified 2026-07-25. Implemented in `R/sysdata-encoding.R` (decoder,
accessors) and `data-raw/encode_sysdata_for_release.R` (build step).
Companion to the null's rate-distortion work
(`simulation/v070_program/pkgopt/FINDINGS_prelim.md`).

## The problem this answers

The 0.8.0 tarball was 9.1 MB, of which 8.59 MB was `R/sysdata.rda`. That
clears CRAN's informal 10 MB ceiling and is not a regression — CRAN
accepted 0.7.4 at 7.3 MB with the same 44,616-cell densified surface, and
the resolved null accounts for the difference. The surface had never been
through a storage-design pass, so the release was parked to run one.

## Byte accounting before the pass

Honest xz-compressed size of each object, measured individually:

| object | in memory | on disk |
|---|---|---|
| `empirical_q_hat_surface$quantiles` | 23.2 MB | 4,314 KB |
| `empirical_q_hat_surface$mean` + `$sd` | 3.6 MB | 761 KB |
| `empirical_q_hat_surface$index` | — | 20 KB |
| `fitted_icc_reference_curves$curves` | 8.4 MB | 1,578 KB |
| `delta_null_ecdf` | 5.3 MB | 1,735 KB |
| `icc_reference_curves`, `reference_binary` | — | 3 KB |
| **`sysdata.rda`** | | **8.59 MB** |

## Three findings

**1. The surface was never storing anything a double could hold.** Every
one of the 2,900,040 stored values is an exact multiple of 1e-5 — the
release build has rounded the surface to five decimals since 0.6.1, where
the argument was that Monte-Carlo error is ~1e-2 and the sixth digit is
incompressible noise. Each value therefore carries at most 17 bits of
content in a 64-bit slot. The same is true of the fitted-ICC curves.

**2. The surface's remaining entropy is Monte-Carlo noise, so the only
structure worth exploiting is within-cell monotonicity.** The surface is a
complete 6-D grid (52 F-keys x 6 k x 11 N x 13 q_true x 5 metrics x 13
probabilities). Every cross-cell delta candidate was measured on that
reshaped array and every one lost to plain probability-axis delta:

| candidate | KB |
|---|---|
| delta along probability, byte planes | **2,862** |
| delta along probability, integer | 3,028 |
| delta along probability then q_true | 3,151 |
| dictionary of the 49,404 unique values + codes | 3,225 |
| delta along probability, q_true and N | 3,316 |
| delta along q_true alone | 3,323 |
| shipped doubles | 4,314 |

Adjacent cells are independent 2,000-replicate simulations. Differencing
across k, N, q_true, or scenario subtracts one noise draw from another and
raises the entropy. The dictionary layout (value pooling, proposed
2026-07-23) is exact and beats plain integers on the null, but here it is
dominated: the surface's 59-fold value repetition is already visible to
xz, and the codes cost as much as the values they replace.

**3. The fitted-ICC curves were the unpriced win.** They are smooth glmer
fitted means over a 501-point q-grid — genuinely redundant along q, unlike
the surface. Differencing along q takes them from 1,578 KB to 158 KB, exact.

`$mean` and `$sd` have no reader in `R/`, `tests/`, or `vignettes/`. They
are build products the package never consulted; dropping them is 761 KB.

## What ships

`int-delta-byteplane-v1`: scale to integers at 1e5, difference along the
axis the array is monotone in (probability for the surface, q-grid for the
ICC curves), split the non-negative 16-bit residuals into two raw byte
planes. Decoding is a cumulative sum, 56 ms for the surface, cached in
`.sysdata_cache` on first access.

| | before | after |
|---|---|---|
| surface quantiles | 4,314 KB | 2,875 KB |
| surface `$mean` + `$sd` | 761 KB | dropped |
| fitted-ICC curves | 1,578 KB | 158 KB |
| `sysdata.rda` | 8.59 MB | **4.89 MB** |
| tarball | 9.1 MB | **5.36 MB** |

**Reconstruction is exact, not approximate.** The decoded arrays are
`identical()` to the ones that shipped through 0.7.4. This is the property
that made the pass cheap: no percentile, band, flag, or field-case value
can move, so the release needed no hold-out validation of its own and the
paper needed no number refresh.

## Why not go further

Dropping to 1e-4 resolution costs another 830 KB and 1e-3 another 1,780 KB.
Both are defensible on noise grounds — the underlying q-hat replicates live
on the 501-point inversion grid, so precision below 1e-3 is quantile
interpolation between two achievable values rather than information about
the data-generating process. Neither was taken, because both are lossy and
would require the output-unit scoring pass the null got (percentile read
error and flag-cut movement through the shipped downstream, scored against
the P6 hold-out truth set) plus a paper number-refresh pass. The lossless
encoding already lands the tarball under target. If bytes ever bind again,
`data-raw/encode_sysdata_for_release.R` takes `scale` as an argument and
`simulation/v070_program/g2_holdout/score_surface.R` is the scorer to reuse.

## Verification performed

- Encoder round-trip `identical()` to the pre-encoding archive, both arrays,
  asserted at build time and again in `tests/testthat/test-sysdata-encoding.R`
  against integer-lattice checksums and pinned cells.
- Full suite 849 pass / 0 fail (22 legacy v0.2.0 skips).
- Synthetic case cards byte-identical to `synthetic_cases_vFINAL.out`.
- Card-summary verification reproduces the values currently in
  `05_examples.tex` (the on-disk `verify_card_summary_v080.out` predates the
  three patched aligned-delta percentiles and is stale, not contradictory).
- Field cases at paper precision: Klein 78th / 52nd, Tan 86th / 81st,
  Hinde 73rd / 64th / 74th with delta-hat 0.92, all three Hinde panels
  divergent at the 99.5th percentile.
- Pre-encoding sysdata kept three ways: `data-raw/sysdata_plaindouble_v0.8.0.rda`
  (on disk, gitignored), `PABAK_Investigation/grassr_sysdata_plaindouble_v0.8.0_BACKUP.rda`
  (outside the package tree), and `git show 8657902:R/sysdata.rda`, which is
  byte-identical to both. The archive is gitignored precisely because git
  already holds it — re-committing would duplicate an 8.6 MB blob in a
  history that was deliberately shrunk in July.

## Note for whoever rebuilds sysdata

`encode_sysdata_for_release.R` is a post-processing step, not a builder. The
`data-raw/build_*.R` scripts still write plain doubles including `$mean` and
`$sd`; run the encoder last, after any rebuild, and re-check that the
archive it reads is the plain-double object rather than an already-encoded
one (it refuses to re-encode by asserting the 1e-5 lattice).
